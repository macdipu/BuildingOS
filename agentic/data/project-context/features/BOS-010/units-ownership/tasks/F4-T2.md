# F4-T2 — Building selector, floors and units

## Category
BE (building-service)

## Objective
Building selector/context reads and individual floor/unit setup (UO-01/02/03/09).

## Scope
- `GET /api/v1/me/buildings` (active memberships: building summary + roles, paginated) and
  `GET /api/v1/buildings/{b}` (context + caller roles/capabilities; any active member or platform admin).
- V6 schema: `building_floor`, `building_unit` with per-building composite keys.
- Floors: create/update/list. Units: create/update/list/detail. Six unit types; unit number
  trimmed, unique case-insensitively per building (display spelling kept); area sq ft
  >0 with ≤2 decimals; bedrooms ≥0; maintenance rate ≥0 metadata only, ≤2 decimals.
- Writes: building admin or platform admin, building row lock, expectedVersion on updates,
  audit rows; platform admins acting without admin membership must give a reason.
  SUSPENDED buildings are read-only.
- Activation and reactivation require ≥1 unit and an active building admin, under the
  same building lock as unit writes.

## Implementation notes
Floor/unit reads are building-admin/platform only in this task: owners read only their own
units (UO-D01), which needs ownership allocations (F4-T4). `ownedUnitCount` in My Buildings
lands with F4-T4 for the same reason. Field length limits (unit number 32, floor label 40,
notes 1000) are technical bounds, not business rules.

## Acceptance Criteria
- "4a" then " 4A " in one building → 409; "4A" in another building → allowed.
- Concurrent creates of one normalized number → one success, rest 409.
- Invalid type/area/precision/foreign floor → 400/404 with nothing persisted.
- Activation without a unit → 409 NO_BUILDING_UNIT; after a unit → allowed.
- Cross-building floor/unit IDs → 404; non-admin member → 403; F2 regression passes.
