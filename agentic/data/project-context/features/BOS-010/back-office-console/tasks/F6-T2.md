# F6-T2 — auth-service platform-user/role management (BOC-05)

## Category
BE

## Objective
New internal, service-to-service-only endpoints on `auth-service` for listing platform
users and assigning/revoking platform roles, so `back-office-service` (F6-T4/BOC-05) has
something to call. `auth-service` keeps sole ownership of `User`/`PlatformRole`.

## Scope
- `UserRepository` additions: `findById`, `list(query, role, page, size)`, `count(query, role)`,
  `revokePlatformRole`.
- New use cases (one package per action, mirroring `provisionuser`): `listusers`, `getuser`,
  `assignplatformrole`, `revokeplatformrole`.
- New internal endpoints (not gateway-routed, same posture as `/internal/users/provision`):
  `GET /internal/users?query=&role=&page=&size=`, `GET /internal/users/{id}`,
  `POST /internal/users/{id}/platform-roles`, `DELETE /internal/users/{id}/platform-roles/{role}`.
- Assign/revoke restricted to `SUPER_ADMIN` only; no user may modify their own platform
  roles (extends ID-04's "a building admin cannot self-grant a platform role").
- List/get restricted to `SUPER_ADMIN` or `PLATFORM_ADMIN` (D-07-style identical check).
- Structured log line on every grant/revoke (matches the existing `user_provisioned`
  logging convention; auth-service has no audit table yet, this is not the place to add one).

## Dependencies
F6-T1 (none functionally, but establishes the pattern); existing `provisionuser` use case
and `app_user`/`platform_user_role` schema (already exist since the identity slice).

## Implementation Requirements
Follow docs/ARCHITECTURE.md and the existing `auth-service` conventions exactly: one
package per use case, domain repository interface unchanged in spirit (add methods, no
new domain model needed -- `User`/`PlatformRole` already exist), controller maps
transport to command/query and back, no repository access from the controller.

## Acceptance Criteria
- SUPER_ADMIN can list users, view one, assign a role, revoke a role.
- PLATFORM_ADMIN can list/view but gets 403 on assign/revoke.
- Any other/no role gets 403 on all four; missing/invalid token gets 401.
- A user cannot modify their own platform roles (403), even as SUPER_ADMIN.
- Assigning an already-held role or revoking a role not held is a no-op, not an error.
- Assigning/revoking a role for a nonexistent user returns 404.

## Test Requirements
Integration tests on real Testcontainers Postgres (mirroring
`UserProvisioningIntegrationTest`), `mvn verify` green for auth-service and the reactor.
