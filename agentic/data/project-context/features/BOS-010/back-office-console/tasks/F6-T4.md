# F6-T4 — SupportSession + ElevatedApprovalRequest domain + API (BOC-07)

## Category
BE

## Objective
`back-office-service` owns `SupportSession` and `ElevatedApprovalRequest`: a platform support
user opens a reason-bound, scope-limited, time-boxed session for a target user and/or building;
high-risk scopes need a separate four-eyes `SUPER_ADMIN` approval; every change is audited.
No action relay yet (F6-T4b).

## Scope
- Domain: `SupportSession`, `SupportScope` (D-10 ordinary + high-risk values, `isHighRisk()`),
  `ElevatedApprovalRequest`, `ElevatedApprovalStatus` (PENDING|APPROVED|DENIED), rules below.
- Flyway V4 (if needed): `support_session.end_reason`/`ended_by` style columns only if the
  audit trail cannot live in `lifecycle_transition`; reuse `lifecycle_transition` (add
  `EntityType` values) for session + approval events. Tables already exist in V2.
- Use cases (one package per action): `startsupportsession`, `listsupportsessions`,
  `getsupportsession`, `endsupportsession`, `requestelevatedapproval`,
  `approveelevatedapproval`, `denyelevatedapproval`, `listelevatedapprovals`,
  `checksupportscope`; shared lazy expiry (like `OnboardingSessionExpiry`).
- Outbound ports: reuse auth-service user lookup (target user must exist) and building-service
  building lookup (building must exist) from the onboarding feature — move to `shared` if both
  features need them; do not duplicate clients.
- REST under `/api/v1/platform/backoffice/**`:
  - `POST /support-sessions`
  - `GET  /support-sessions?active=&platformUserId=&targetUserId=&buildingId=&page=&size=`
  - `GET  /support-sessions/{id}` (includes its approval requests)
  - `POST /support-sessions/{id}/end`
  - `POST /support-sessions/{id}/elevated-approvals` (`{scope, reason}`)
  - `GET  /elevated-approvals?status=&page=&size=`
  - `POST /elevated-approvals/{id}/{approve|deny}` (`{reason}`)
  - `GET  /support-sessions/{id}/scope-check?scope=` → `ALLOWED | PENDING_APPROVAL | NOT_GRANTED | SESSION_ENDED`
- OpenAPI contract entries.

## Rules (D-36, D-10, §149.12)
- Start: caller holds `SUPPORT_AGENT`, `PLATFORM_ADMIN` or `SUPER_ADMIN`; `platform_user_id`
  = caller; target user and/or building required (at least one) and must exist; reason
  required; one or more D-10 scopes; `expires_at` in the future and at most
  `buildingos.support.max-duration` (default `PT8H`) after start.
- High-risk scopes (`SUPPORT_REVERSE_PAYMENT`, `SUPPORT_TRANSFER_OWNERSHIP`,
  `SUPPORT_REMOVE_BUILDING_ADMIN`, `SUPPORT_EXPORT_FINANCIAL_UNRESTRICTED`) are not granted
  directly: requesting one (at start or later, by the owner) creates a `PENDING`
  `ElevatedApprovalRequest`; ordinary scopes are granted at start.
- Approve/deny: `SUPER_ADMIN` only, and not the session owner (four-eyes) → otherwise 403;
  only `PENDING` requests on an active session; decision reason required on deny.
- An approval is valid only while its session is active; a denied scope may be re-requested
  (one `PENDING` per session+scope, already enforced by a unique index → 409).
- End: owner, `SUPER_ADMIN` or `PLATFORM_ADMIN`; ending an ended/expired session → 409.
- Visibility: `SUPER_ADMIN`/`PLATFORM_ADMIN` see all; `SUPPORT_AGENT` sees only own (others
  404); any other caller 403.
- Active session past `expires_at` is persisted as ended (system, no actor) before any read or
  change; pending approvals on an ended session become unusable.
- Every session start/end and every approval request/decision appends a
  `lifecycle_transition` row with actor and timestamp.

## Acceptance Criteria
- Start validation: bad scope/reason/expiry/no target → 400; unknown user/building → 422;
  dependency down → 503 and nothing stored; non-support caller → 403.
- High-risk scope at start → session created with ordinary scopes + PENDING request; scope-check
  returns `PENDING_APPROVAL` until a different SUPER_ADMIN approves, then `ALLOWED`.
- Owner-SUPER_ADMIN approving own request → 403; PLATFORM_ADMIN approving → 403.
- Expired session reports ended, scope-check `SESSION_ENDED`, changes → 409.
- Audit rows for every event.
