# F6-T7 — Buildings + Subscriptions screens (BOC-03/04)

## Category
FE

## Objective
Back-office operators review building applications, run building lifecycle actions, and
manage plans/fees, all through the existing building-service and subscription-service APIs.

## Scope
Buildings (§149.2–149.7):
- Applications / Under Review lists: `GET /api/v1/platform/building-applications?status=`
  (SUBMITTED, UNDER_REVIEW, MORE_INFORMATION_REQUIRED, REJECTED, APPROVED); status tabs use the
  §149.4 state names, not the mockup kanban (UI-INDEX C-3).
- Application review page per §149.5: applicant identity/contact, relationship, building
  details, verification documents, submission date, review history
  (`GET /api/v1/building-applications/{id}/history`), internal notes (`…/notes`), duplicate
  matches (`…/duplicates`), actions Start Review / Request Information / Reject / Approve
  (approve requires the recorded creation fee, D-24/D-26; initial admin phone prefilled, D-12).
- Onboarding / Active / Suspended building lists + building detail with Activate / Suspend /
  Reactivate (`/api/v1/platform/buildings/{id}/…`). via F6-T7a (D-34).
- Archived Buildings: explicit "not available yet" (BOC-03, AP-09).
Subscriptions (§149.15–149.16, D-22..D-27):
- Plans: list/create/edit/retire (`/api/v1/platform/subscription-plans*`) with §149.16
  entitlement keys as structured fields, not marketing bullets.
- Free tier / feature entitlement defaults (`/api/v1/platform/free-tier`).
- Fees: building-creation fee record + payments (`/api/v1/platform/fees/{feeCode}*`, D-24).
- Per-user subscription lookup and plan assignment (`/api/v1/platform/users/{userId}/subscription`).
- Building Subscriptions / Trials / Past Due / Suspended lists: via F6-T7b (D-35), named as user subscriptions; Trials / Past Due hidden until those states exist.

## Dependencies
F6-T6. F6-T7a, F6-T7b for the building and subscription lists (rest can proceed).

## Implementation Requirements
Reuse existing endpoints unchanged; every mutation shows the backend error code on failure;
optimistic-version (`expectedVersion`) conflicts surface as a refresh prompt.

## Acceptance Criteria
- Operator can take an application SUBMITTED → UNDER_REVIEW → APPROVED/REJECTED/MORE_INFO with
  notes, and sees history + duplicate matches; approve is blocked with a clear message when the
  creation fee is not recorded.
- Plan CRUD round-trips; unknown entitlement keys are rejected by the API and shown inline.
- No SaaS revenue/collection metrics, auto-pay, invoices, VAT or dunning UI (C-2, §149.23).

## Test Requirements
Component tests for review actions and plan form validation; Playwright: review→approve flow
against local stack; lint/typecheck/test green.

## UI Reference
- `ui/stitch/back-office/02-building-onboarding-pipeline` — list/table + side review panel layout.
- `ui/stitch/back-office/03-society-subscriptions-billing` — plan cards + table layout.
- BRD §149.3–149.7, §149.15–149.16, §149.23. UI-only excluded: kanban stages, RAJUK/sub-registry
  KYC, escrow/bank sync, per-building DB/subdomain, "Issue Production Keys", revenue KPIs,
  auto-pay/direct debit, VAT invoices, MRR ledger export (C-2, C-3).
